## 四、最快的验收方式：跑冒烟脚本

一条命令覆盖 55 项断言（认证、下单、支付、履约、统计、越权、黑名单）：

```powershell
# 确保后端已启动
powershell -ExecutionPolicy Bypass -File scripts/smoke-test.ps1
```

预期输出结尾：

```
======================================
  通过 55 项 / 失败 0 项
======================================
```

**注意两点**：

1. 脚本会**真实下单**，重复执行会累积测试订单；第二次跑之前建议先 `DROP DATABASE takeout` 重建（或接受数据累积）。
2. 登录接口有「同 IP 10 次/分钟」限流。**连续两次运行请间隔 1 分钟以上**，否则会看到 `15003 请求过于频繁` 并连带失败一片 —— 那是限流生效，不是功能坏了。

## 五、★ 重点检查哪些业务（按优先级）

系统有 11 个业务模块，但**不要平均用力**。下面 5 块是「出错代价最高」和「最容易被误判为正常」的地方。

### 优先级 1：双 token 认证链路 —— 最容易被误判

**为什么重点查**：它坏掉的表现是「用着用着突然要重新登录」，很容易被当成"正常过期"而放过。而且它是所有权限的地基。

**要重点确认的 4 件事**：

| 确认点                            | 为什么关键                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| access 过期能自动续期，用户无感知 | 这是双 token 存在的全部意义                                                          |
| **并发请求只刷新一次**            | 刷新风暴的根源；10 个并发请求同时 401 会打 10 次 refresh，导致令牌互相作废、用户被踢 |
| refresh 用过一次就失效（旋转）    | 防令牌泄露重放；如果旧 refresh 还能用，说明旋转没生效                                |
| 登出后 access 立即失效（黑名单）  | 否则"登出"只是前端删了本地 token，服务端仍认旧令牌                                   |

**代码位置**：后端 [JwtUtil.java](../backend/src/main/java/com/takeout/common/util/JwtUtil.java)、[AuthenticationFilter.java](../backend/src/main/java/com/takeout/common/filter/AuthenticationFilter.java)、[AuthServiceImpl.java](../backend/src/main/java/com/takeout/auth/service/impl/AuthServiceImpl.java)；前端两个工程的 `src/utils/request.js`。

**⚠️ 一个特别容易踩的坑**：`accessToken` 过期时后端返回的是 **HTTP 401 + 响应体 `code=40101`**。前端必须**先读响应体里的 code**再决定动作。如果写成「HTTP 401 就跳登录页」，自动续期永远不会触发（开发中管理员后台就踩了这个坑，已修）。

### 优先级 2：订单状态机 —— 出错会直接造成资损

**为什么重点查**：状态机破防的表现是「已取消的订单还能被接单」「已完成的订单还能再取消」，一旦发生就是钱和库存对不上。

**要重点确认的 3 件事**：

1. **非法流转被拒**：对已完成(50)的订单调接单/取消接口，必须返回 `14002`，不能成功。
2. **取消必须归还库存**：下单扣库存 → 取消 → 库存必须回到原值。**这是最容易漏的一环**（只改状态忘了还库存）。
3. **销量只在完成时累加**：完成(50)加销量；取消链路不回退销量（因为压根没加）。

**代码位置**：流转表在 [OrderStatusEnum.java](../backend/src/main/java/com/takeout/common/enums/OrderStatusEnum.java)，全部变更强制走 [OrderStatusMachine.java](../backend/src/main/java/com/takeout/order/service/OrderStatusMachine.java) 的 `transfer()`（校验 + 改状态 + 写日志三合一，不存在"改了状态没留痕"）。库存归还/销量累加在 [OrderServiceImpl.java](../backend/src/main/java/com/takeout/order/service/impl/OrderServiceImpl.java)。

**设计要点（值得理解）**：销量在「完成」时累加而不是「支付」时，是为了让取消链路完全不需要回退销量 —— 一条规则贯穿，避免两处口径打架。

### 优先级 3：金额重算与起送价 —— 直接关系钱

**为什么重点查**：只要前端能影响金额，就是资损。

**要重点确认的 2 件事**：

1. **下单接口不接受任何价格字段**：请求体只有 `dishId + quantity`，前端传 `price: 0.01` 也不会被采纳。
2. **起送价在服务端校验**：绕过前端直接调接口、只点一个低于起送价的菜，必须返回 `14003`。

**验证方法**：用 Swagger 或 Postman 直接调 `POST /api/customer/order`，手动构造请求体，故意加一个 `price` 字段 —— 返回的 `payAmount` 必须仍按数据库价格算。

**代码位置**：`OrderServiceImpl.createOrder()` 第 ⑤⑥ 步。

### 优先级 4：数据权限（越权）—— 安全事故高发区

**为什么重点查**：越权是这类系统最常见、后果最严重的漏洞（A 能看到 B 的订单和地址）。

**要重点确认的 3 件事**：

| 场景                     | 预期                   | 为什么这么设计                                            |
| ------------------------ | ---------------------- | --------------------------------------------------------- |
| 顾客 B 查看顾客 A 的订单 | `14004 无权操作该订单` | 订单归属校验在 Service 层做，`userId` 只从 Token 上下文取 |
| 商家 B 操作商家 A 的订单 | `14004`                | 同上，商家身份通过 `merchant.user_id` 反查                |
| 顾客 token 调商家接口    | `403`                  | 端级授权按路径前缀统一拦截，新增接口不会漏配              |

**要理解的关键设计**：`UserContextHolder` 里的 `userId` 是数据归属校验的**唯一可信来源**。全项目没有任何一个接口接受前端传入的 `userId` 作为权限依据 —— 这是能说"不会被越权"的底气所在。

**代码位置**：端级在 [UserTypeInterceptor.java](../backend/src/main/java/com/takeout/common/interceptor/UserTypeInterceptor.java)，数据级在各 Service 的 `requireOwned()` / `requireCustomerOrder()` 等方法。

### 优先级 5：商家端店铺归属 + 库存

- **店铺归属**：商家只能改自己的分类/菜品/店铺。验证方式：用 `merchant2` 的 token 调 `PUT /api/merchant/dish/{merchant1的菜品id}`，必须被拒。
- **库存原子扣减**：`UPDATE dish SET stock = stock - ? WHERE id = ? AND stock >= ?` —— 把"库存够不够"的判断下沉到 WHERE 条件，靠数据库行锁防超卖，不需要应用层加锁。**验收方式是并发下单**（第六节 F5）。

## 六、手工验收步骤（F1~F8）

### F1 双 token 自动续期（最重要，5 分钟）

```ini
# 1) 把 .env 里访问令牌有效期临时改短
ACCESS_TOKEN_TTL=10s
```

重启后端 → 浏览器登录顾客端 → 打开 F12 的 Network 面板 → **停留 10 秒**（不要操作）→ 点击「我的订单」。

**预期现象（全部满足才算通过）**：

- 出现一次 `POST /api/auth/refresh`，返回 200 并带**新的** accessToken 与 refreshToken
- 紧接着 `GET /api/customer/order` 返回 200（**用新令牌重放了原请求**）
- 页面上**没有**任何"登录已过期"的提示，你完全无感知
- 刷新后再次点其他页面（如购物车），**不再触发新的 refresh**

**如果失败会看到**：直接跳回登录页（说明续期没触发，踩了 HTTP 401 的坑）；或每点一下都刷新一次（说明并发去重没生效）。

> 验完记得把 `ACCESS_TOKEN_TTL` 改回 `30m`。

**再加一个强化验证（并发去重）**：把 `ACCESS_TOKEN_TTL=10s`，登录后立刻在浏览器控制台执行：

```js
Promise.all(
  Array.from({ length: 8 }, () =>
    fetch("/api/customer/cart", {
      headers: {
        Authorization: "Bearer " + localStorage.getItem("h5_access_token"),
      },
    }),
  ),
);
```

**预期**：Network 里 `/auth/refresh` **只出现 1 次**（8 个请求共用同一次刷新）。

### F2 顾客主链路（5 分钟）

1. customer1 登录 → 首页能看到「川味小厨」「轻食沙拉铺」（**待审核烧烤摊不应出现**）
2. 进川味小厨 → 加「宫保鸡丁」×2 +「麻婆豆腐」×1 → 底部栏件数为 3、金额 70.00
3. 购物车里确认金额相同 → 去结算 → 选地址 → 提交订单
4. My 订单 → 待支付 tab → 点「去支付」→ 支付成功 → 订单变「待接单」
5. 数据库确认（可选）：`orders.pay_amount` = 73.00，`order_item` 里菜名/单价是快照值

### F3 商家履约链路（3 分钟）

1. merchant1 登录后台 → 订单管理 → 待接单 tab 看到刚才的订单
2. 点「接单」→ 状态变备餐中 → 点「出餐」→ 配送中 → 点「送达」→ 已完成
3. 回顾客端刷新订单详情 → 状态时间轴有 4 条记录，操作方分别显示「顾客 / 系统 / 商家」

### F4 金额防篡改（2 分钟）

Swagger 里调 `POST /api/customer/order`，请求体**故意加价格字段**：

```json
{
  "addressId": 1,
  "items": [{ "dishId": 2, "quantity": 1, "price": 0.01 }],
  "remark": "改价攻击测试"
}
```

**预期**：返回的 `payAmount` 仍是按数据库价格的真实金额（26 + 配送费），**不是 0.01**。

### F5 并发不超卖（3 分钟，加分项）

1. 商家端把「麻婆豆腐」库存改成 5
2. 用脚本并发下 10 单（或多人同时点）
3. **预期**：只有 5 单成功，其余返回 `12005 库存不足`；`SELECT stock FROM dish WHERE id=3` 结果必须为 **0**，绝不能为负数

### F6 越权验证（3 分钟）

1. Swagger 用 customer1 登录拿 token
2. 调 `GET /api/customer/order/1`（不是自己的订单）→ 预期 `14004`
3. 同 token 调 `GET /api/merchant/order` → 预期 `403`
4. 注册一个新顾客 → 调 `GET /api/customer/order` → 预期只能看到自己的（`total=0`）

### F7 密码加密验证（1 分钟）

```sql
SELECT username, password, LENGTH(password) FROM sys_user;
```

**预期**：`password` 全是 `$2a$10$` 开头的 60 字符密文，长度都是 60。若看到任何明文（如 `123456`），说明加密链路漏了。

再确认接口不泄露密码：

```powershell
# 用任意已登录 token
Invoke-RestMethod -Uri "http://localhost:8080/api/auth/me" -Headers @{Authorization="Bearer <token>"}
```

**预期**：返回体里**没有** `password` 字段。

### F8 超时未支付自动取消（加分项，需等 15 分钟）

1. 下一单但**不支付**
2. 把 `.env` 的 `takeout.order.pay-timeout-minutes` 临时改成 `1` 并重启（重启后本地缓存清空，注意重新登录）
3. 等 1~2 分钟
4. **预期**：订单变「已取消」，取消原因是「超过 1 分钟未支付，系统自动取消」，**菜品库存已归还**

## 七、已知限制与设计取舍（验收时不要当成 Bug）

| 项                               | 说明                                                                                                                                              |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 支付是模拟的                     | 调 `/payment/{orderNo}/pay` 直接置为已支付。真实支付的接入点已预留：把 `PaymentServiceImpl.pay()` 里「标记已支付 + 通知订单模块」搬进异步回调即可 |
| 支付单是懒创建的                 | 下单时不建支付单，首次进入支付流程才按订单金额生成。原因：模块依赖方向定为 `payment → order` 单向，避免环形依赖                                   |
| 无评价 / 菜品规格 / 平台退款     | 方案里明确列入二期；状态 70（已退款）已占位但流转表暂未启用                                                                                       |
| 无骑手端                         | 一期范围外，配送由商家自行完成（出餐 → 送达）                                                                                                     |
| 无操作日志表                     | 方案表清单里就没有它；关键操作留痕靠 `order_status_log`                                                                                           |
| 平台看板无月份趋势               | 只有商家端有按日趋势；平台侧提供排行                                                                                                              |
| `sys_user` 逻辑删除 + 账号唯一键 | 当前没有"注销账号"接口，所以不会触发；**将来加注销功能时要注意**：逻辑删除后同名账号无法重新注册（同 `cart_item` 踩过的坑）                       |
| 限流阈值                         | 登录 10 次/分钟/IP、失败 5 次锁定 10 分钟。快速重复跑冒烟脚本会命中，等 1 分钟即可                                                                |
| 本地缓存是单机实现               | `CACHE_TYPE=local` 时黑名单/限流不跨实例。多副本部署必须切 `redis`                                                                                |

这些不是"演示"，是本次实现中真实踩到并修掉的问题，值得在验收时特别留意是否复发：

| #   | 问题                                 | 表现                                         | 根因                                                                                                                              | 修法                                                                    |
| --- | ------------------------------------ | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 1   | 顾客注册接口不可用                   | `/customer/user/register` 返回 401「未认证」 | 该接口在认证白名单里，但落在 `/customer/**` 前缀下，被端级授权拦截器要求"先登录才能注册"                                          | 拦截器增加白名单放行                                                    |
| 2   | **购物车"移除后再加同一菜品"报 500** | 加购接口返回 500 系统异常                    | `cart_item` 有唯一索引 `(user_id, dish_id)`，但 MyBatis-Plus 逻辑删除只把 `del_flag` 置 1、行还在表里，重新加购插入新行时撞唯一键 | 购物车改为**物理删除**（`CartItem` 不继承带 `delFlag` 的 `BaseEntity`） |
| 3   | 访问不存在的路径返回 500             | 应 404 却报"系统异常"                        | Spring 6 起静态资源找不到抛 `NoResourceFoundException`，被兜底异常处理当成系统异常                                                | 单独处理该异常返回 404                                                  |
| 4   | 管理员后台自动续期不生效             | access 一过期就直接跳登录页                  | 后端用「HTTP 401 + body.code=40101」表达令牌过期，前端在 HTTP 错误分支里一见 401 就登出                                           | 错误分支优先读 `error.response.data.code`                               |

> 第 2 条最值得记住：**逻辑删除 + 唯一索引是一对天然冲突的组合**。以后给任何表加唯一键时，先想清楚这张表会不会用逻辑删除。

## 九、常见问题排查

| 现象                                       | 原因 / 处理                                                                                           |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 启动报「JWT 密钥未配置或长度小于 32 字符」 | `.env` 的 `JWT_SECRET` 被误删或改短了，恢复默认值即可                                                 |
| 启动报数据库连接失败                       | `.env` 的 `MYSQL_PASSWORD` 没填或填错；确认 MySQL 已启动                                              |
| 登录返回 `15003 请求过于频繁`              | 触发登录限流，等 1 分钟                                                                               |
| 登录返回 `10002 账号已停用`                | 该账号被管理后台停用了                                                                                |
| 顾客端 401 且不自动续期                    | 检查 `refreshToken` 是否还在 localStorage；或看 Network 里 `/auth/refresh` 的返回                     |
| 前端调接口 404                             | 检查 Vite 代理：应把 `/api` 代理到 `http://localhost:8080` **且不做 rewrite**（后端自带 `/api` 前缀） |
| 图片上传后显示不出来                       | 返回的 `url` 形如 `/upload/2026/09/24/x.jpg`，展示时需拼上 `/api` 前缀                                |
| 重启后登录态失效                           | `CACHE_TYPE=local` 时 refresh 记录存在进程内存里，重启即清空。生产切 redis 可避免                     |
| 想彻底重来                                 | `DROP DATABASE takeout;` 再重启后端                                                                   |
