## 零、一个能省你很多时间的习惯

看到不认识的注解，**先看它的 `import` 是哪一行**。同一个注解名字，可能来自完全不同的库。

本项目里就藏着一个经典的坑：

```java
// 这是 MyBatis 的，标在数据库访问接口上
import org.apache.ibatis.annotations.Mapper;
public interface SysUserMapper extends BaseMapper<SysUser> { }

// 这是 MapStruct 的，标在对象转换接口上
import org.mapstruct.Mapper;
public interface UserConvert { }
```

**两个都叫 `@Mapper`，作用完全不同。** 只看名字会彻底懵——「为什么这个 Mapper 里没有 SQL？」

有一个可靠的判断方法：

- `interface XxxMapper extends BaseMapper<Xxx>` → MyBatis，管数据库
- `interface XxxConvert` 且方法只有 `toVO / toEntity` → MapStruct，管对象转换

## 第一部分 · 注解速查

每行四列：**注解 → 一句话作用 → 本项目真实位置 → 不用它会怎样**。

### 1. 启动与装配（只在 `TakeoutApplication` 上用）

| 注解                                   | 作用                                         | 真实位置             | 不用会怎样                                                         |
| -------------------------------------- | -------------------------------------------- | -------------------- | ------------------------------------------------------------------ |
| `@SpringBootApplication`               | 启动类的标志，内含自动配置                   | `TakeoutApplication` | 程序没有入口                                                       |
| `@ConfigurationPropertiesScan`         | 自动扫描 `@ConfigurationProperties` 类并注册 | `TakeoutApplication` | `.env` / `application.yml` 里的配置读不进 Java 对象，全注入成 null |
| `@MapperScan("com.takeout.**.mapper")` | 告诉 MyBatis 去哪找 Mapper                   | `TakeoutApplication` | 每个 Mapper 都要手动写 `@Mapper`，漏一个就注入失败                 |
| `@EnableScheduling`                    | 开启定时任务                                 | `TakeoutApplication` | `@Scheduled` 静默失效——**超时订单永远不会被自动取消，且不报错**    |
| `@EnableAsync`                         | 开启异步方法                                 | `TakeoutApplication` | `@Async` 失效                                                      |

> 💡 `@EnableScheduling` 这条特别值得记：忘记加它，定时任务不会报错、不会启动，只是**什么都不做**。这种「静默失效」是排查成本最高的一类问题。

### 2. Web 层

| 注解                                                        | 作用                                     | 真实位置                                             | 不用会怎样                                       |
| ----------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------- | ------------------------------------------------ |
| `@RestController`                                           | 标记这是 HTTP 接口类，返回值自动转 JSON  | 所有 `controller` 类                                 | 返回的是视图名，前端收到 404 或 HTML             |
| `@RequestMapping("/customer/order")`                        | 类级别的路径前缀                         | 每个 Controller 类头                                 | 接口路径会变成方法级路径，全部对不上             |
| `@GetMapping` `@PostMapping` `@PutMapping` `@DeleteMapping` | 具体路径 + HTTP 方法                     | 各个方法                                             | 必须用 `@RequestMapping(method=...)` 写一长串    |
| `@RequestBody`                                              | 把请求体 JSON 反序列化成 Java 对象       | `create(@Validated @RequestBody CreateOrderDTO dto)` | 参数是 null（不会报错，会 NullPointerException） |
| `@PathVariable`                                             | 从 URL 路径里取值（`/order/{id}` 的 id） | `@PathVariable Long id`                              | 取不到值，参数为 null                            |
| `@RequestParam`                                             | 从 `?a=1` 查询串里取值                   | `FileController` 的 `@RequestParam("file")`          | 同上                                             |
| `@Validated`                                                | 触发参数校验注解                         | 几乎所有接口入参                                     | **校验注解全部失效**，脏数据直接进业务逻辑       |
| `@RestControllerAdvice`                                     | 全局异常处理器的标志                     | `GlobalExceptionHandler`                             | 异常直接抛给前端变成 500 HTML，前端解析不了      |
| `@ExceptionHandler(XxxException.class)`                     | 指定这个方法处理哪类异常                 | `GlobalExceptionHandler` 里 12 个方法                | 同上                                             |

### 3. 依赖注入与配置

| 注解                                                           | 作用                                      | 真实位置                                                                  | 不用会怎样                                                |
| -------------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------- |
| `@Component`                                                   | 交给 Spring 管理的通用组件                | `LocalCacheClient`、`LoginUserLoaderImpl`、各切面                         | 类不会被创建，注入它时启动失败                            |
| `@Service`                                                     | 同上，语义上表示「业务服务」              | 所有 `XxxServiceImpl`、`XxxApiImpl`                                       | 同上                                                      |
| `@Configuration`                                               | 标记配置类（里面放 `@Bean`）              | `WebConfig`、`MybatisPlusConfig`                                          | `@Bean` 不生效                                            |
| `@Bean`                                                        | 手动创建对象交给 Spring                   | `PasswordConfig` 里的 `BCryptPasswordEncoder`、`WebConfig` 里的过滤器注册 | 拿不到这个对象                                            |
| `@RequiredArgsConstructor`                                     | **Lombok**：为所有 `final` 字段生成构造器 | 几乎每个 Service/Controller 类                                            | 要手写一长串构造器，或者改用 `@Autowired`                 |
| `@ConfigurationProperties(prefix = "takeout.jwt")`             | 把配置文件里 `takeout.jwt.*` 绑定到这个类 | `JwtProperties` 等 5 个 properties 类                                     | 配置读不进来                                              |
| `@ConditionalOnProperty(name = "type", havingValue = "redis")` | 满足条件才创建这个 Bean                   | `RedisCacheClient` / `LocalCacheClient`                                   | 缓存的两个实现会同时存在，Spring 不知道注入哪个而启动失败 |

> 💡 `@RequiredArgsConstructor` 是**本项目最常用的注解**。为什么不用 `@Autowired`？因为构造器注入能让字段是 `final`（不可变），而且**依赖缺失时启动就报错**，不会等到运行时才 NPE。

### 4. 数据层

| 注解                                   | 作用                                    | 真实位置                                            | 不用会怎样                                                    |
| -------------------------------------- | --------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------- |
| `@Mapper`（MyBatis）                   | 标记数据库访问接口，由 MyBatis 生成实现 | 所有 `XxxMapper`                                    | 注入失败                                                      |
| `@TableName("orders")`                 | 指定实体对应哪张表                      | `Order` 实体                                        | 默认按类名找表，`Order` 会去找 `order` 表（保留字，SQL 报错） |
| `@TableId(type = IdType.AUTO)`         | 主键自增策略                            | `BaseEntity`、`OrderItem` 等                        | 插数据时主键策略不对                                          |
| `@TableField(fill = FieldFill.INSERT)` | 插入时自动填充该字段                    | `BaseEntity` 的 createTime/createBy                 | 审计字段永远是 null                                           |
| `@TableField("del_flag")`              | Java 字段名与列名不一致时手动指定       | `BaseEntity.delFlag`                                | 找不到列                                                      |
| `@Param("merchantId")`                 | 给 SQL 里的 `#{merchantId}` 起名        | `DishMapper.deductStock`                            | 多参数时必须写，否则报参数找不到                              |
| `@Select` `@Update`                    | 直接在接口方法上写 SQL                  | `OrderMapper` 的统计 SQL、`DishMapper` 三个原子操作 | 要额外写 XML 文件                                             |

> ⚠️ **本项目没有用 `@TableLogic`**。逻辑删除是靠 `application.yml` 里的全局配置生效的：
>
> ```yaml
> mybatis-plus:
>   global-config:
>     db-config:
>       logic-delete-field: delFlag # 只要实体有 delFlag 字段就自动逻辑删除
> ```
>
> 这带来一个**必须知道的后果**：实体有没有 `delFlag` 字段，决定了删除是「标记」还是「真删」。
> `cart_item` 表当初就是因为「逻辑删除 + 唯一索引」打架才出的 bug——购物车实体**故意不继承 `BaseEntity`**，所以没有 `delFlag`，删除是真删。详见 `02-common` 篇。

### 5. 事务

| 注解                                            | 作用                               | 真实位置                  | 不用会怎样                                     |
| ----------------------------------------------- | ---------------------------------- | ------------------------- | ---------------------------------------------- |
| `@Transactional(rollbackFor = Exception.class)` | 方法内所有数据库操作是一个原子操作 | 所有写操作的 Service 方法 | 中途失败会留下「订单建了但库存没扣」这种脏数据 |

> ⚠️ 两个高频坑：
>
> 1. **必须写 `rollbackFor = Exception.class`**。默认只对 `RuntimeException` 回滚，业务异常若继承自 `Exception` 就不会回滚。
> 2. **同一个类内部自己调自己，注解会失效**（因为不走 Spring 代理）。本项目 `OrderTimeoutTask`（定时任务）和 `OrderServiceImpl`（事务方法）**故意拆成两个类**，就是为了避开这个坑——代码注释里写了原因。

### 6. 参数校验

| 注解                  | 作用                               | 例子                                                    |
| --------------------- | ---------------------------------- | ------------------------------------------------------- |
| `@NotBlank`           | 字符串不能为 null / 空串 / 空白    | `@NotBlank(message = "下单菜品不能为空")`               |
| `@NotNull`            | 对象不能为 null                    | `@NotNull(message = "请选择收货地址")`                  |
| `@NotEmpty`           | 集合不能为空                       | `CreateOrderDTO.items`                                  |
| `@Size(min, max)`     | 长度范围                           | `@Size(min = 6, max = 20)`                              |
| `@Min` `@Max`         | 数值范围                           | `@Max(value = 99, message = "单个菜品数量不能超过 99")` |
| `@Pattern(regexp)`    | 正则                               | 手机号 `^1[3-9]\\d{9}$`                                 |
| `@DecimalMin("0.01")` | 小数下限                           | 菜品价格                                                |
| `@Valid`              | **级联校验**：校验集合里的每个元素 | `CreateOrderDTO` 里的 `List<OrderItemDTO>`              |

> ⚠️ 这些注解**只有配合 `@Validated` 才生效**。而且它们只做「格式」校验，业务规则校验（库存够不够、店铺开没开门）必须在 Service 里用 `BusinessException` 手动抛。

### 7. Lombok（编译期生成样板代码）

| 注解                                   | 生成什么                                           | 真实位置                           |
| -------------------------------------- | -------------------------------------------------- | ---------------------------------- |
| `@Data`                                | getter + setter + equals + hashCode + toString     | 几乎所有实体和 VO                  |
| `@Getter`                              | 只生成 getter                                      | 所有枚举                           |
| `@Builder`                             | 链式创建对象：`Result.builder().code(200).build()` | `Result`、`LoginUser`、各种契约 VO |
| `@AllArgsConstructor`                  | 全参构造器（枚举里配合 `@Getter` 用）              | `ResultCode`、`UserTypeEnum`       |
| `@EqualsAndHashCode(callSuper = true)` | 生成 equals/hashCode 时**带上父类字段**            | 所有继承 `BaseEntity` 的实体       |
| `@Slf4j`                               | 生成一个 `log` 对象                                | 各个 Service 实现类                |
| `@RequiredArgsConstructor`             | 为 `final` 字段生成构造器                          | 见上文                             |

> ⚠️ `@EqualsAndHashCode(callSuper = true)` 不加会怎样？父类 `BaseEntity` 的字段（如 id）不参与比较，两个 id 不同但其他字段相同的对象会被判定为「相等」。业务上一般不出问题，但排查时会很困惑。

### 8. MapStruct（对象转换）

| 注解                                         | 作用                           | 真实位置                                             |
| -------------------------------------------- | ------------------------------ | ---------------------------------------------------- |
| `@Mapper`（MapStruct）                       | 标记转换接口，编译期生成实现类 | 所有 `XxxConvert`                                    |
| `@Mapping(target = "userId", source = "id")` | 字段名不一致时手动指定对应关系 | `UserConvert.toAuthVO`、`MerchantConvert.toSimpleVO` |
| `@Mapping(target = "xxx", ignore = true)`    | 忽略某个字段不映射             | `UserConvert.toEntity`（**故意忽略 password**）      |

**两个必须知道的事**：

1. **生成的实现类在 `backend/target/generated-sources/annotations/` 下**。想知道 `@Mapping` 到底干了什么，直接打开 `UserConvertImpl.java` 看——这是排查转换问题的真相来源。
2. **`ignore = true` 有时是安全设计**。`UserConvert.toEntity()` 忽略 `password`，是为了让「DTO 里的明文密码」没有任何路径进入实体——这样即使某个 Service 忘了加密，也不会明文入库。

### 9. AOP（切面）

| 注解                                 | 作用                                   | 真实位置                                                    |
| ------------------------------------ | -------------------------------------- | ----------------------------------------------------------- |
| `@Aspect`                            | 标记这是一个切面类                     | `RateLimitAspect`、`IdempotentAspect`、`RepeatSubmitAspect` |
| `@Before("@annotation(rateLimit)")`  | 在目标方法**执行前**插入逻辑           | 限流、防重提交                                              |
| `@Around("@annotation(idempotent)")` | 包裹目标方法（前后都能插手）           | 幂等（因为失败时要释放标记，必须能拿到异常）                |
| `@annotation(xxx)`                   | 切点表达式：只切「标了这个注解的方法」 | 三个切面都用它                                              |

**为什么 `@Before` 和 `@Around` 要分开用？** 看 `IdempotentAspect` 的注释：它需要在方法**失败时**把幂等标记删掉（允许用户重试），所以必须能拿到返回值/异常 → 只能用 `@Around`。

### 10. 定时任务

| 注解                                                     | 作用                             | 真实位置                                                                |
| -------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------- |
| `@Scheduled(initialDelay = 30_000, fixedDelay = 60_000)` | 启动 30 秒后开始，每 60 秒跑一次 | `OrderTimeoutTask`、`PaymentCloseTask`、`LocalCacheClient.cleanExpired` |

注意参数区别：`fixedDelay`（上次**结束后**再等 N 毫秒）vs `fixedRate`（按固定频率）。本项目用 `fixedDelay`，避免上一次没跑完就叠加执行。

### 11. 接口文档（Swagger）

| 注解                                                | 作用                                    |
| --------------------------------------------------- | --------------------------------------- |
| `@Tag(name = "顾客端-订单")`                        | 给一组接口起名（显示在 Swagger 页面上） |
| `@Operation(summary = "下单", description = "...")` | 给单个接口加说明                        |
| `@Schema(description = "订单号")`                   | 给字段加说明                            |

## 第二部分 · 高频语法专题

这些不是注解，但你会频繁看到、且容易卡住。

### 1. `LambdaQueryWrapper` 链式查询 ⭐ 最重要

**它是什么**：MyBatis-Plus 提供的条件构造器，用 Java 方法代替手写 SQL 字符串。

**真实位置**：`UserServiceImpl.page()`、`OrderServiceImpl.baseWrapper()`

```java
Wrappers.<SysUser>lambdaQuery()
    .select(SysUser::getId, SysUser::getUsername, SysUser::getPhone)   // ①
    .eq(query.getUserType() != null, SysUser::getUserType, query.getUserType())  // ②
    .and(w -> w.like(SysUser::getUsername, kw)                          // ③
            .or().like(SysUser::getNickname, kw))
    .orderByDesc(SysUser::getCreateTime);                              // ④
```

**逐点读懂**：

- **① `.select(...)`**：只查这几列。不写它会变成 `SELECT *` —— 项目规范禁止 `SELECT *`，因为会把 `password` 密文无谓地捞进内存。
- **② `.eq(布尔条件, 字段, 值)`**：**这个三参数重载是本项目用得最多的写法**。第一个参数为 `false` 时，这个条件**整条不生效**。
  等价于手写：`if (userType != null) { sql += " and user_type = ?" }`。
  好处：不用写一堆 `if` 来拼 SQL。
- **③ `.and(w -> ...)`**：**加括号，这是最容易出错的地方**。
  如果不加 `.and(...)` 包一层，生成的 SQL 会是：
  `WHERE user_type = ? AND username LIKE ? OR nickname LIKE ?`
  因为 `AND` 优先级高于 `OR`，`OR nickname LIKE ?` 会**击穿前面的身份过滤**，把其他身份的账号也查出来。
  加了 `.and(...)` 才变成正确的：`WHERE user_type = ? AND (username LIKE ? OR nickname LIKE ?)`
- **④ `.orderByDesc(...)`**：对应 `ORDER BY xxx DESC`。

**其他常见方法**：`.in(字段, 集合)`、`.lt/.gt`（小于/大于）、`.last("limit 1")`（拼在 SQL 末尾）。

### 2. 方法引用 `SysUser::getId`

**它是「字段名」，不是「取值」。**

```java
.select(SysUser::getId)               // 拿到的是列名 "id"，不是调用 getId()
.eq(SysUser::getUserType, 1)          // 同上，拿到列名
PageResult.of(page, this::toVOWithDesc)  // 这里是把「方法」当参数传
```

同一个 `::` 有两种用途：

- 传给 MyBatis-Plus → 它通过反射解析出**对应的数据库列名**
- 传给 `Function` / `Consumer` 这类函数式接口 → 它调用**这个方法本身**

看不懂的时候看一眼方法参数的类型就清楚了：参数要 `SFunction`（MyBatis-Plus 的）就是列名，要 `Function` 就是真调用。

### 3. Stream 与 Collectors

**真实位置**：`OrderServiceImpl.assemblePage()`、`CartServiceImpl.list()`

```java
// ① 把 List 转成「按 key 分组的 Map」
Map<Long, List<OrderItem>> itemMap = items.stream()
        .collect(Collectors.groupingBy(OrderItem::getOrderId));

// ② 把 List 转成「id -> 对象」的 Map
Map<Long, DishSimpleVO> dishMap = dishes.stream()
        .collect(Collectors.toMap(DishSimpleVO::getDishId, d -> d, (a, b) -> a));
//                            key 取什么 ────────┘   value 取什么 ┘   key 重复了怎么办 ┘

// ③ 求和（BigDecimal 的求和要配合 reduce）
BigDecimal total = items.stream().map(CartItemVO::getAmount)
        .reduce(BigDecimal.ZERO, BigDecimal::add);

// ④ 求件数总和
int count = items.stream().mapToInt(CartItemVO::getQuantity).sum();
```

**① 为什么 `toMap` 需要第三个参数？**
如果两个元素的 key 相同，`toMap` 会直接抛 `IllegalStateException: Duplicate key`。第三个参数 `(a, b) -> a` 表示「重复时保留先出现的那个」。
👉 **本项目里这个参数是必需的**：批量查询时如果数据有异常重复，没有它整个接口就崩了。

**② `reduce(BigDecimal.ZERO, BigDecimal::add)` 是在做什么？**
从 0 开始，把每个元素依次 `add` 进去。等价于一个循环累加，但写成了链式。

### 4. `record`（Java 16+ 语法糖）

**真实位置**：`LocalCacheClient` 里的 `Entry`

```java
private record Entry(String value, long expireAt) {
    boolean expired() {
        return expireAt > 0 && System.currentTimeMillis() > expireAt;
    }
}
```

一行代码等于以前要写 30 行：不可变类 + 全参构造器 + getter + equals/hashCode/toString。

**读法注意**：取值是 `entry.value()`，**不是** `entry.getValue()`——record 的访问器名字就是字段名本身，没有 `get` 前缀。

### 5. `switch` 表达式（箭头语法）

**真实位置**：`OrderStatusMachine.transfer()`

```java
switch (target) {
    case PENDING_ACCEPT -> update.setPayTime(now);
    case PREPARING -> update.setAcceptTime(now);
    case COMPLETED -> update.setFinishTime(now);
    case CANCELED -> {
        update.setCancelTime(now);
        update.setCancelReason(remark);
    }
    default -> { }
}
```

和老的 `switch` 的区别：

- `->` 后面直接写逻辑，**不用写 `break`**
- **不会「穿透」**（fall-through）：老的 switch 忘了 break 会继续执行下一个 case，这是经典 bug；箭头语法从语法上杜绝了
- 多行逻辑用 `{ }` 包起来
- **必须穷尽所有情况或写 `default`**，否则编译不过

### 6. `BigDecimal`（算钱）

**真实位置**：`OrderServiceImpl.createOrder()` 第 ⑤ 步

```java
BigDecimal amount = dish.getPrice().multiply(BigDecimal.valueOf(quantity));
BigDecimal totalAmount = totalAmount.add(amount);
if (totalAmount.compareTo(minAmount) < 0) { ... }   // 比大小用 compareTo
```

**三条必须记住的**：

1. **绝不能用 `double` / `float` 算钱**。`0.1 + 0.2` 在浮点数里等于 `0.30000000000000004`，累加几十次后金额就对不上账了。
2. **比大小必须用 `compareTo`，不能用 `==` 或 `equals`**。
   - `==` 比较的是对象引用，永远是 false
   - `equals` 连**精度**一起比：`new BigDecimal("38.0").equals(new BigDecimal("38.00"))` 结果是 **false**！
   - `compareTo` 只比数值大小：`38.0` vs `38.00` 返回 0（相等）✅
3. `BigDecimal` 是不可变的，`add()` **不会**修改原对象，必须接收返回值：
   `totalAmount.add(x)` 单独一行是无效代码（编译器不报错，但金额没变）。

### 7. 泛型 `<T>`

**真实位置**：`Result`、`PageResult`

```java
public static <T> Result<T> ok(T data) { ... }     // 静态方法要自己声明 <T>
public class Result<T> { private T data; }          // 类上声明一次，方法里都能用

// 调用时 T 由编译器推断：
Result<Void> r1 = Result.ok();                      // T = Void
Result<TokenVO> r2 = Result.ok(tokenVO);            // T = TokenVO
```

**为什么静态方法要单独写 `<T>`？** 因为静态方法不属于任何实例，类上的 `<T>` 对它不可见。这是初学者最常见的困惑之一。

### 8. 枚举 + 静态 Map（状态机流转表）

**真实位置**：`OrderStatusEnum`

```java
@Getter
@AllArgsConstructor
public enum OrderStatusEnum {
    PENDING_PAYMENT(10, "待支付"),
    PENDING_ACCEPT(20, "待接单");
    // ...

    private final Integer code;
    private final String desc;

    // 流转表：key = 当前状态，value = 允许到达的状态
    private static final Map<Integer, Set<Integer>> TRANSITIONS = Map.of(
            PENDING_PAYMENT.code, Set.of(PENDING_ACCEPT.code, CANCELED.code),
            PENDING_ACCEPT.code, Set.of(PREPARING.code, CANCELED.code)
    );

    public static boolean canTransfer(Integer from, Integer to) {
        return TRANSITIONS.getOrDefault(from, Set.of()).contains(to);
    }
}
```

**这个设计好在哪**：把「订单状态怎么流转」这条规则集中在一处声明。
如果不这样写，就要在「接单」「拒单」「取消」「确认收货」十几个方法里各写一遍 `if`，早晚有一个入口漏判，把已取消的订单改成已完成。

**顺带一个语法点**：`Map.of(...)` 最多只支持 **10 个键值对**（Java 的限制）。本项目正好 4 个，够用。

### 9. Lambda 与函数式接口

**真实位置**：`UserServiceImpl.page()`、`PageResult.of()`

```java
// ① Consumer：接收参数，没有返回值
.and(w -> w.like(SysUser::getUsername, kw).or().like(SysUser::getNickname, kw))
//   ↑ w 就是外面传进来的 wrapper 自己

// ② Function：接收一个，返回一个
public static <E, T> PageResult<T> of(IPage<E> page, Function<E, T> mapper) {
    ...page.getRecords().stream().map(mapper)...
}
// 调用处：
PageResult.of(page, this::toVOWithDesc)   // 把「怎么转换」当参数传进来
```

**为什么这么设计**：`PageResult` 是通用的分页容器，它**不知道**每个业务模块要把 entity 转成什么 VO。把「转换方法」当参数传进来，它就能复用于所有模块——这就是「策略模式」用 Lambda 表达的写法。

### 10. `static final` 常量类的私有构造器

```java
public final class SecurityConstants {
    private SecurityConstants() { }     // ← 私有构造器

    public static final String AUTH_HEADER = "Authorization";
}
```

- `final class`：不能被继承
- `private` 构造器：**不能被 new**，只能通过 `SecurityConstants.AUTH_HEADER` 使用

**这是个约定的写法**：工具类/常量类不应该被实例化。不加私有构造器不会报错，但别人可能写出 `new SecurityConstants()` 这种没有意义的代码。

## 第三部分 · 遇到看不懂的代码，按这个顺序查

1. **看注解的 `import`** —— 解决「同名不同库」（比如 `@Mapper`）
2. **看方法的返回类型** —— 解决「这段在干什么」（返回 `Result<T>` 就是接口返回值）
3. **用 IDE 的「Find Usages / 查找用法」** —— 解决「谁在调用它」。**这个功能比任何文档都有用**，比追问代码怎么用快得多。
4. **看生成的代码** —— MapStruct 看 `target/generated-sources/annotations/`；MyBatis 的 SQL 可以打开 `logging.level.com.takeout: debug` 看真实执行的 SQL
5. **本导读** —— 查注解、查模块职责
6. **`docs/接口文档.md`** —— 查前端调的是什么
