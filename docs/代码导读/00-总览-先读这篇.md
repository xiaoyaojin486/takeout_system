## 一、一句话认识这个系统

一个外卖平台，三种角色共用一个后端：

| 端       | 谁在用     | 前端工程                               | 端口 |
| -------- | ---------- | -------------------------------------- | ---- |
| 顾客端   | 点外卖的人 | `frontend-h5`（Vue + Vant，手机界面）  | 5173 |
| 商家端   | 开店的老板 | `frontend-admin`（Vue + Element Plus） | 5174 |
| 管理后台 | 平台运营   | 同上（同一工程，按身份切换菜单）       | 5174 |

后端是一个 **Spring Boot 单体**，但内部按业务切成了 **12 个互不越界的包（模块）**。这是理解整个项目的第一把钥匙：**代码不是按「层」铺开的，而是先按「业务」切开，每个业务内部再分层。**

```
com.takeout/
├── common/      ← 地基：公共能力，不含任何业务
├── auth/        ← 业务模块：认证
├── user/        ← 业务模块：账号
├── merchant/    ← 业务模块：店铺
├── category/    ← 业务模块：菜品分类
├── dish/        ← 业务模块：菜品
├── cart/        ← 业务模块：购物车
├── address/     ← 业务模块：收货地址
├── order/       ← 业务模块：订单（最核心）
├── payment/     ← 业务模块：支付
├── stats/       ← 业务模块：统计看板
└── file/        ← 业务模块：文件上传
```

## 二、12 个模块的单词与职责

> 你反馈「模块的英文单词和各模块负责啥不懂」——这张表就是答案。建议先只记**中文那一列**，英文名读代码时自然就熟了。

| 包名       | 中文     | 一句话职责                                                      | 拥有哪些表                               | 阅读权重       |
| ---------- | -------- | --------------------------------------------------------------- | ---------------------------------------- | -------------- |
| `common`   | 公共能力 | 地基。统一返回体、异常处理、**双 token 工具**、缓存、注解与切面 | 无                                       | ★★★ 必读       |
| `auth`     | 认证     | 三端登录、签发/刷新/登出令牌。回答「你是谁」                    | 无（只读写缓存）                         | ★★★ 必读       |
| `user`     | 账号     | 三端共用一张账号表：注册、资料、改密、管理员管账号              | `sys_user`                               | ★★ 精读        |
| `order`    | 订单     | 状态机、事务、扣库存、快照。回答「谁买了什么、钱对不对」        | `orders` `order_item` `order_status_log` | ★★★ 必读       |
| `merchant` | 店铺     | 商家入驻、审核、营业状态、起送价与配送费                        | `merchant`                               | ★★ 精读        |
| `dish`     | 菜品     | 菜品增删改上下架，以及**原子扣库存的 SQL**                      | `dish`                                   | ★★ 精读        |
| `cart`     | 购物车   | 暂存「想买什么」，按店铺分组，价格实时算不快照                  | `cart_item`                              | ★★ 精读        |
| `payment`  | 支付     | 模拟支付、与订单状态联动                                        | `payment`                                | ★★ 精读        |
| `address`  | 收货地址 | 地址增删改 + 默认地址维护                                       | `address`                                | ★ 略读         |
| `category` | 分类     | 菜品分类，顾客端菜单按它分组                                    | `category`                               | ★ 略读         |
| `stats`    | 统计     | 只做聚合编排，**自己不拥有任何表**                              | 无                                       | ★ 略读         |
| `file`     | 文件     | 图片上传到本地磁盘，返回可访问 URL                              | 无                                       | ☆ 知道在哪就行 |

**只记这几个词就够用了**：merchant 商家 / category 分类 / dish 菜品 / order 订单 / cart 购物车 / payment 支付 / stats 统计 / file 文件。剩下的 `auth`（认证）、`user`（用户）、`address`（地址）是日常英语。

## 三、依赖方向：一条不能破的红线

```
三端前端
   ↓  HTTP
controller  →  service  →  mapper  →  数据库
                ↓
        其他模块的 xxx-api（只有接口和 DTO/VO）
                ↓
             common（大家都能用）
```

三条规则，读代码时可以随时拿来对照：

1. **`common` 不依赖任何业务模块。** 反过来，所有业务模块都可以用 `common`。
   👉 事实核对：全项目有 **66 个文件、共 176 处** `import com.takeout.common.*`。
2. **业务模块之间只能通过对方的 `xxx-api` 包通信。** 比如订单要拿菜品价格，只能调 `DishApi`，**不许**直接查 `dish` 表。
   👉 这就是为什么每个模块里都有一个 `api` 子包——它是这个模块的「对外窗口」。
3. **每个模块只能改自己的表。** `order` 模块碰不到 `dish` 表，扣库存必须走 `DishApi.deductStock()`。

> **为什么这么设计（这才是重点）**：将来某天订单服务要独立部署成一个微服务，你只需要把 `DishApi` 的本地调用换成 HTTP 调用，**业务代码一行不用改**。如果当初直接写了 SQL join 别人的表，就永远拆不开了。

## 四、每个业务模块内部长什么样（八件套）

12 个模块长得几乎一模一样，认识一套就认识全部。以 `dish` 为例：

| 子包                       | 放什么             | 一句话理解                   | 能不能被其他模块用 |
| -------------------------- | ------------------ | ---------------------------- | ------------------ |
| `api/`                     | 对外接口 + 契约 VO | 这个模块的「窗口」           | ✅ 只能用它        |
| `api/impl/`                | 上面接口的实现     | 窗口后面的接线员             | ❌                 |
| `controller/`              | HTTP 入口          | 收参数、做校验、转给 service | ❌                 |
| `service/` `service/impl/` | 业务逻辑 + 事务    | 真正干活的地方               | ❌                 |
| `mapper/`                  | 数据库访问         | 只写 SQL，不写业务           | ❌                 |
| `entity/`                  | 对应数据库表的类   | 只在模块内部流转             | ❌                 |
| `dto/`                     | 接收前端参数       | 进来的数据                   | ❌                 |
| `vo/`                      | 返回前端的数据     | 出去的数据                   | ❌                 |
| `convert/`                 | 对象互转           | entity 转 vo 的翻译官        | ❌                 |

**记住一句话**：`entity` 绝不返回给前端。前端看到的是 `vo`，前端传进来的是 `dto`。

## 五、一次请求的完整旅程（本篇最值得读的一节）

光看目录结构是抽象的。用「顾客点提交订单」这一件事，把整条路走一遍——**读懂了这条链路，你就有能力自己看懂另外 90% 的代码**。

接口：`POST /api/customer/order`

| #   | 经过谁                                        | 做什么                                                            | 关键点                                         |
| --- | --------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| 1   | 前端 `OrderConfirm.vue`                       | 组装请求体，带一次性 `X-Idempotent-Token`                         | 只传 `dishId + quantity`，**不传价格**         |
| 2   | Vite 代理                                     | 把 `/api` 转发到 `localhost:8080`                                 | 不 rewrite，后端自带 `/api` 前缀               |
| 3   | `common/filter/AuthenticationFilter`          | 解析 `Bearer` 令牌 → 查黑名单 → 加载登录用户 → 存进 `ThreadLocal` | **鉴权第一道闸**，六步顺序不能乱（见 02 篇）   |
| 4   | `common/interceptor/UserTypeInterceptor`      | 路径以 `/customer/` 开头 → 要求身份必须是顾客                     | **授权第二道闸**，按路径前缀统一卡             |
| 5   | `common/aspect/IdempotentAspect`              | 检查幂等键，重复提交直接拒绝                                      | 防「网络抖动重发」造成两笔订单                 |
| 6   | `order/controller/CustomerOrderController`    | 参数校验（`@Validated`）后转给 Service                            | Controller 不写业务                            |
| 7   | `OrderServiceImpl.createOrder()` **开始事务** | ① 校验地址归属 → 调 `AddressApi`                                  | 跨模块只走 api                                 |
| 8   | 同上                                          | ② 批量查菜品 → 调 `DishApi.listSimpleByIds`                       | 一次批量查，避免 N+1                           |
| 9   | 同上                                          | ③ 校验所有菜品属于同一店铺 → 否则拒绝                             | 一个订单只能属于一个商家                       |
| 10  | 同上                                          | ④ 校验店铺已审核且营业中 → 调 `MerchantApi`                       | 未审核的店不能下单                             |
| 11  | 同上                                          | ⑤ **后端重算金额** + 校验起送价                                   | 前端传的价格一律不认                           |
| 12  | 同上                                          | ⑥ 写 `orders` 表（地址快照）                                      | 地址是快照，之后改地址不影响历史单             |
| 13  | 同上                                          | ⑦ 循环 `DishApi.deductStock()` → 写 `order_item`（菜品快照）      | 任一菜品扣减失败 → **整单回滚**                |
| 14  | `common/config/AuditMetaObjectHandler`        | 自动填 `create_by / create_time`                                  | 业务代码里看不到一行 setCreateTime             |
| 15  | `order/service/OrderStatusMachine`            | 写 `order_status_log`（0 → 10 待支付）                            | 状态变更与留痕绑在一起，不可能只改状态不记日志 |
| 16  | `cart/api/CartApiImpl`                        | 把已下单的菜品从购物车移除                                        | 保留同店未下单的其他菜                         |
| 17  | —                                             | **事务提交**                                                      | 从第 7 步到第 16 步是一个原子操作              |

**涉及的表**：写 `orders`、`order_item`、`order_status_log`、改 `dish`（扣库存）、删 `cart_item`。

> 建议你现在就打开 `OrderServiceImpl.createOrder()`，对着上面这张表读一遍。代码里的注释就是在解释每一步「为什么」。

## 六、推荐阅读顺序（不要按文件夹字母序读）

**三条主线，按顺序吃透，约能拿到 60% 的收获：**

**主线 1 · 地基（先读 `common`，1~2 小时）**
`Result` → `GlobalExceptionHandler` → `AuthenticationFilter` → `JwtUtil` → `CacheClient`
👉 读完你能回答：**一个请求进来，怎么确定「你是谁」；出了错，怎么统一变成 JSON。**

**主线 2 · 认证（再读 `auth` + `user`，1 小时）**
`AuthController` → `AuthServiceImpl`（login / refresh / logout 三个方法）
👉 读完你能回答：**双 token 为什么能防令牌泄露；为什么登出之后旧令牌立刻失效。**

**主线 3 · 订单（最后读 `order`，2~3 小时）**
`OrderServiceImpl.createOrder()` → `OrderStatusMachine` → `DishMapper.deductStock()`
👉 读完你能回答：**为什么并发下单不会超卖；为什么取消订单要归还库存。**

**其余 9 个模块**：等你读完主线就会发现它们只是「同一套八件套换个业务名词」，此时可以每个模块只看 3 个文件：`entity`（表长什么样）、`service/impl` 的公开方法（业务规则）、`controller`（对外接口）。

## 七、怎么判断自己读懂了

每个模块篇的末尾都有 **3 个自检问题，不给答案**。这是刻意设计的：

- **能答出来** → 这个模块可以过了，不用再逐行读。
- **答不出来但知道去哪找** → 也算过关（真实工作中就是查着写）。
- **完全不知道从哪找** → 回头把这一篇的「精读文件」再看一遍。

不要追求「全部看懂」。这个项目有 192 个 Java 文件、上千个方法，**没有人会全部记住**。目标只是：**给你一个需求，你知道该动哪个模块的哪个文件。**

---

## 八、三个反面模式（照着做会浪费很多时间）

1. **不要从 `entity` 开始逐个读。** 它们是数据库表的映射，读起来很枯燥、收获也最小。应该从 `controller`（对外有什么能力）倒着读进来。
2. **不要试图记住所有方法。** 需要的时候用 IDE 的「查找用法（Find Usages）」比背下来有用得多。
3. **不要跳过 `common` 直接读业务。** `common` 里有 49 个文件、是被引用最多的地方。跳过它，你后面每次看到 `Result`、`BusinessException`、`UserContextHolder` 都会卡住。
