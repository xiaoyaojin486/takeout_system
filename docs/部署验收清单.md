# 外卖系统 · 部署验收清单

部署完成后，按本清单**逐项**打勾。每项都给出「命令 → 预期结果」，不通过时看「排查」一列。

> 约定：`<IP>` = 目标机 IP；所有命令在**目标机**上执行（除标注「控」的项在 WSL2 控制节点执行）。

## C. 负载均衡分流

### C1 连续请求被分到两个后端
```bash
# 打 10 次，然后分别看两个后端日志
for i in $(seq 10); do curl -s -o /dev/null http://<IP>/api/error; done
echo "--- backend-1 ---"; docker logs takeout-backend-1 --tail=20 | grep -c "GET /api/error"
echo "--- backend-2 ---"; docker logs takeout-backend-2 --tail=20 | grep -c "GET /api/error"
```
**预期**：两个计数**都大于 0**（轮询把请求分给了两个实例）。

**排查**：若只有一个实例有日志，检查 `deploy/nginx/nginx.conf` 的 upstream 是否两个 server 都在。

- [ ] 通过

### C2 网关指向两个上游
```bash
docker exec takeout-nginx cat /etc/nginx/conf.d/default.conf | sed -n '/upstream/,/}/p'
```
**预期**：看到 `server backend-1:8080 ...` 与 `server backend-2:8080 ...`，且都带 `max_fails=2 fail_timeout=10s`。

- [ ] 通过

### C3 换策略可生效（可选，展示用）
编辑 `deploy/nginx/nginx.conf`，在 upstream 里加上 `ip_hash;`（或把某个 server 改成 `weight=7`），
重新发布后观察分流变化：
```bash
cd /opt/takeout-src/deploy/ansible && ansible-playbook site.yml --ask-vault-pass
```
**预期**：加 `ip_hash` 后，同一客户端请求固定落到同一实例。

- [ ] 通过

## D. 故障高可用（本清单最重要的部分）

### D1 停掉 backend-1 后服务仍然可用
```bash
docker stop takeout-backend-1
# 连续请求，观察返回码
for i in $(seq 10); do curl -s -o /dev/null -w "%{http_code} " http://<IP>/; done; echo
```
**预期**：**全部 200**（Nginx 把请求全部转给 backend-2；前 1~2 次可能因 max_fails 计数略慢，之后稳定）。

- [ ] 通过

### D2 故障节点被自动剔除
```bash
docker logs takeout-backend-2 --tail=30 | grep -c "GET /"      # 应持续增长
curl -s -o /dev/null -w "%{http_code}\n" http://<IP>/api/error  # 仍 200
```
**预期**：backend-2 日志持续增长，接口仍 200。

- [ ] 通过

### D3 恢复后自动重新纳入
```bash
docker start takeout-backend-1
sleep 15     # 等 fail_timeout(10s) + 后端启动
for i in $(seq 10); do curl -s -o /dev/null http://<IP>/api/error; done
docker logs takeout-backend-1 --tail=20 | grep -c "GET /api/error"
```
**预期**：backend-1 重新收到请求（计数 > 0）。

- [ ] 通过

## E. 共享状态（多实例必须共享的两样东西）

### E1 缓存确实走 Redis（不是本地缓存）
```bash
docker exec takeout-backend-1 env | grep CACHE_TYPE
docker exec takeout-redis redis-cli -a "$(grep REDIS_PASSWORD /opt/takeout/.env | cut -d= -f2)" keys '*' | head
```
**预期**：`CACHE_TYPE=redis`；Redis 里有 key（说明登录态/黑名单确实写在 Redis）。

- [ ] 通过

### E2 登出后旧 token 在两个实例都失效（跨实例共享验证）
1. 用顾客账号登录，拿到 `accessToken`
2. 调登出接口
3. 用**同一个**旧 token 请求需要登录的接口

**预期**：返回 401 / 未登录。
（若 `CACHE_TYPE=local`，会有 50% 概率被另一个实例放行 —— 这正是必须用 Redis 的原因。）

- [ ] 通过

### E3 文件确实走 MinIO（不是本地磁盘）
```bash
docker exec takeout-backend-1 env | grep FILE_STORAGE_TYPE
docker exec takeout-minio ls -l /data/takeout 2>/dev/null | head
```
**预期**：`FILE_STORAGE_TYPE=minio`；MinIO 数据目录下出现 `takeout` 桶目录。

- [ ] 通过

### E4 上传的图片两个实例都能访问
1. 在 `http://<IP>:81/` 商家端上传一张菜品图片，拿到返回的 `url`（形如 `/files/2026/10/13/xxxx.jpg`）
2. 连续多次访问该图片（会分别落到两个后端）：
```bash
for i in $(seq 6); do curl -s -o /dev/null -w "%{http_code} " http://<IP>/files/<返回的路径>; done; echo
```
**预期**：**全部 200**（文件在 MinIO 里共享，不依赖某个实例的本地磁盘）。

- [ ] 通过

## G. 监控（Zabbix）

### G1 Agent 已安装并运行
```bash
systemctl is-active zabbix-agent2
systemctl is-enabled zabbix-agent2
```
**预期**：`active` 且 `enabled`。

- [ ] 通过

### G2 自定义监控项能取到值
```bash
/usr/sbin/zabbix_agent2 -t "takeout.tcp[80]"
/usr/sbin/zabbix_agent2 -t "takeout.tcp[3306]"
/usr/sbin/zabbix_agent2 -t "takeout.tcp[6379]"
/usr/sbin/zabbix_agent2 -t "takeout.tcp[9000]"
```
**预期**：每行都返回 `[t|1]`（1 = 端口在监听）。
把对应容器停掉再测，应返回 `[t|0]`。

- [ ] 通过

### G3 HTTP 状态码监控项可用
```bash
/usr/sbin/zabbix_agent2 -t "takeout.http[127.0.0.1,80]"
```
**预期**：返回 `[t|200]`。

- [ ] 通过

### G4 备份心跳可被监控
```bash
/usr/sbin/zabbix_agent2 -t "vfs.file.time[/opt/takeout/status/last_success,modify]"
stat -c '%y' /opt/takeout/status/last_success
```
**预期**：返回一个 Unix 时间戳；`stat` 显示的时间 = 最后一次成功备份时间（跑完 F2 后应是刚刚）。

在 Zabbix Web 上给该监控项配触发器：`now() - last(...) > 86400` → 超过 24 小时没成功备份就告警。

- [ ] 通过

## H. 日志与端口安全

### H1 容器日志有轮转上限
```bash
cat /etc/docker/daemon.json
```
**预期**：`log-opts` 里 `max-size: 10m`、`max-file: 3`。

- [ ] 通过

### H2 主机日志已落盘并设了上限
```bash
journalctl --disk-usage
grep -E '^(Storage|SystemMaxUse)' /etc/systemd/journald.conf
```
**预期**：`Storage=persistent`、`SystemMaxUse=200M`；磁盘占用不超过该上限。

- [ ] 通过

### H3 内部端口未对外暴露
```bash
ss -tlnH | awk '{print $4}' | sort -u
```
**预期**：
- `0.0.0.0:80`、`0.0.0.0:81`（对外，符合预期）
- `127.0.0.1:3306`、`127.0.0.1:6379`、`127.0.0.1:9000`、`127.0.0.1:18080`、`127.0.0.1:18081`
  （**只绑 127.0.0.1**，局域网访问不到）
- 不应出现 `0.0.0.0:3306` / `0.0.0.0:6379` 这类暴露

- [ ] 通过

## 验收结论

| 结果 | 判断 |
|------|------|
| A ~ F 全部通过 | **部署合格**，具备「Nginx 负载均衡 + 容器高可用 + 共享缓存/存储 + 双备份」完整能力 |
| A ~ D 通过，E/F 部分不通过 | 功能可用，但多实例共享或备份链路有隐患，需修完再交付 |
| A/B 不通过 | 部署未成功，回到 `docs/部署文档.md` 第七节排查 |

**向面试官演示的最小剧本（约 3 分钟）**：

1. `docker compose ps` 展示 6 个容器 + `curl http://<IP>/` 返回 200
2. 打 10 次接口，`docker logs` 展示两个后端交替收到请求（负载均衡）
3. `docker stop takeout-backend-1`，`curl` 仍返回 200（故障自动剔除）
4. `docker start takeout-backend-1`，日志展示它重新收到请求（自动恢复）
5. `/opt/takeout/backup/backup-db.sh` 展示本地 + MinIO 双份备份
