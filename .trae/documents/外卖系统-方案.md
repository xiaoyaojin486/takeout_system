# 外卖系统 · 技术方案

> 架构范式沿用「模块单体化」规范：common 承载公共能力，业务模块之间只通过各自 `xxx-api` 契约通信。
> 落地形态参考同级「绩效管理系统」：单 Maven 工程 + 包级模块隔离 + `controller / service / mapper / entity / dto / vo / convert / api` 八件套。

---

## 一、目标与范围

### 1.1 三端业务闭环

| 端 | 使用者 | 一期核心能力 |
| --- | --- | --- |
| 顾客端（H5） | 普通用户 | 注册登录、浏览店铺与菜品、购物车、收货地址、下单、模拟支付、订单跟踪、取消/确认收货 |
| 商家端（桌面） | 入驻商家 | 店铺信息与营业状态、分类管理、菜品管理（上下架/库存）、订单接单/拒单/出餐、营业统计 |
| 管理后台（桌面） | 平台管理员 | 商家审核与状态管理、用户管理、全平台订单总览、平台数据看板 |

### 1.2 分期

- **一期（核心闭环）**：上表全部能力 + 双 token 鉴权 + BCrypt 密码加密 + 超时未支付自动取消。
- **二期（增强）**：订单评价、菜品规格/口味、平台介入退款（状态 70）、菜品搜索优化、消息通知。

### 1.3 明确不做（一期）

骑手端与配送调度、真实第三方支付对接（预留回调接口位）、优惠券/满减营销、多商家购物车合并结算。

每个业务模块严格按此结构组织（以 `dish` 为例）：

│   ├── MerchantDishController.java   # /api/merchant/dish
│   └── CustomerDishController.java   # /api/customer/dish
├── service/
│   ├── DishService.java
│   └── impl/DishServiceImpl.java
├── mapper/DishMapper.java

├── dto/DishDTO.java  DishQuery.java  DishStatusDTO.java
├── vo/DishVO.java
└── convert/DishConvert.java
```

**依赖红线**（与提示词一致，评审时逐条核对）：

- `controller → service → mapper → entity`，事务注解只加在 Service 且显式 `rollbackFor`。
- 跨模块**只能**注入对方的 `XxxApi`，禁止注入对方的 Service / Mapper / Entity。
- `entity` 不返回前端，`dto/vo/query` 与 `entity` 不互相继承。
- 无循环依赖。典型闭环风险点已规避：`order` 通过 `user-api`、`merchant-api`、`dish-api` 取数，反向模块（如 `dish`）不回调 `order`。

### 4.3 订单状态机

```
                  ┌──────────────── 顾客取消 / 15分钟超时未支付 ────────────────┐
                  ▼                                                             │
  [10 待支付] ──支付成功──> [20 待接单] ──商家接单──> [30 备餐中] ──出餐──> [40 配送中] ──> [50 已完成]
                              │                        │                      │
                              └── 商家拒单 / 顾客取消 ──┴──────────────────────┘
                                             ▼
                                      [60 已取消]
```

| 起点 | 终点 | 触发方 | 附加动作 |
| --- | --- | --- | --- |
| 10 | 20 | 系统（支付成功） | 写入 `pay_time`，支付单置已支付 |
| 10 | 60 | 顾客 / 定时任务 | 归还库存 |
| 20 | 30 | 商家 | 写入 `accept_time` |
| 20 | 60 | 商家拒单 / 顾客取消 | 归还库存，已支付则标记待退款（二期走 70） |
| 30 | 40 | 商家 | — |
| 40 | 50 | 顾客确认 / 商家送达 | 累加菜品销量、店铺销量、写入 `finish_time` |
| — | 其他组合 | — | 一律抛 `ORDER_STATUS_ERROR` |

**库存与销量策略（一条规则贯穿，避免来回冲抵）**

- 下单即扣库存，用 `UPDATE dish SET stock = stock - #{qty} WHERE id = #{id} AND stock >= #{qty}` 原子扣减，影响行数为 0 即库存不足 —— 无锁防超卖。
- 订单进入「已取消」时归还库存。
- 销量只在订单「已完成」时累加，取消链路无需回退销量。

## 五、认证与安全设计（核心）

### 5.1 双 token 设计

| 令牌 | 有效期 | Claims | 存储 |
| --- | --- | --- | --- |
| accessToken | 30 分钟 | `sub`=userId、`username`、`ut`=userType、`type`=access、`jti` | 前端内存 / localStorage |
| refreshToken | 7 天 | `sub`=userId、`type`=refresh、`jti` | 前端 localStorage + 服务端 `CacheClient` |

- **按 jti 多端共存**：同一账号在 H5、商家端、后台可同时登录，刷新互不影响。
- **刷新即旋转**：每次 refresh 作废旧 refresh（删缓存 key），签发全新一对令牌，旧 refresh 再用直接判失效。
- **登出即拉黑**：access 的 `jti` 写入黑名单，TTL = 该令牌剩余有效期（到期自动清理，不无限膨胀）；refresh 缓存直接删除。
- **状态联动**：刷新时回查用户 `status`，账号被停用/删除则 refresh 一并失效。

**缓存 key 规范**（local / redis 双实现共用）：

```
auth:refresh:{jti}    -> userId
auth:blacklist:{jti}  -> "1"
```

**后端校验链路**

```
请求 → AuthenticationFilter
        ├─ 白名单（Ant 匹配，OPTIONS 直接放行）
        ├─ 解析 Bearer accessToken
        ├─ 校验 type == access（refresh 冒充 access 直接拒绝）
        ├─ 校验 jti 不在黑名单
        ├─ LoginUserLoader 加载 LoginUser（userId/username/userType/nickname/...）
        └─ 绑定 UserContextHolder(ThreadLocal)，finally 强制 clear 防线程池串号
```

异常统一落 `Result`：`40101` 访问令牌已过期（前端触发刷新）、`40102` 刷新令牌已失效（前端清态跳登录）、`401` 未认证。

**前端自动续期（两个前端工程同一套实现）**

```
请求拦截器：Authorization: Bearer {accessToken}

响应拦截器：
  code == 40101 且非 /auth/refresh 自身
      → 取 refreshToken 调 /api/auth/refresh
      → 成功：落库新 pair，重放被中断的请求
      → 失败 / code == 40102：清空登录态 → 跳登录页
  code == 403：仅提示无权限，不跳登录页
```

必须处理的两个细节，否则线上必现「刷新风暴」：

1. **并发去重**：模块级 `refreshPromise` 单例，同一时刻多个 401 只发一次刷新请求，其余请求 `await` 同一个 Promise。
2. **防死循环**：刷新接口自身的请求/响应不参与重试逻辑；重放请求携带版本号，避免旧 token 覆盖新 token 后再次 401。

### 5.2 密码加密

- `BCryptPasswordEncoder` 统一 Bean（`PasswordConfig`），`strength` 默认 10，自带随机盐。
- 注册 / 管理员重置密码 → `encoder.encode(raw)`；登录 → `encoder.matches(raw, encoded)`。
- 数据库只存密文；**任何 VO 不得包含 password 字段**，Mapper 查询显式列字段，禁止 `SELECT *`。
- 前端登录密码经 HTTPS 明文提交后由后端加密落库（不引入前端加盐，避免伪安全）。

### 5.3 权限模型

**端级权限（粗粒度）**：路径前缀 + `@RequiresUserType` 注解 + AOP 校验

| 路径前缀 | 允许 user_type |
| --- | --- |
| `/api/auth/**` | 白名单（登录、刷新） |
| `/api/customer/**` | 1 顾客 |
| `/api/merchant/**` | 2 商家 |
| `/api/admin/**` | 3 管理员 |
| `/api/file/upload` | 任意已登录 |

**登录端校验**：`POST /api/auth/login` 入参带 `clientType`，与账号 `user_type` 不匹配时统一返回「用户名或密码错误」，不泄露账号类型是否存在。

**数据权限（细粒度，Service 层校验）**：

- 顾客：订单/地址/购物车/评价一律以 `UserContextHolder` 中的 `userId` 作为查询条件，禁止用前端传入的 `userId`。
- 商家：菜品/分类/订单操作前校验 `merchant.user_id == 当前登录 userId`，越权抛 `DATA_SCOPE_DENIED`。

**安全加固**：

| 项 | 措施 |
| --- | --- |
| 暴力破解 | 登录接口 `@RateLimit`（同 IP + 账号 5 次/分钟），失败次数入缓存 |
| 重复下单 | 下单接口 `@RepeatSubmit` + `@Idempotent`（令牌桶 key = userId + 幂等 token） |
| 越权查询 | 全链路 `userId` 取自 Token 上下文，非请求参数 |
| 金额篡改 | 前端只传 `dishId + quantity`，金额由后端重算，不信任任何前端价格 |
| CORS | 白名单指定前端域名，不用 `*` |
| 敏感信息 | 生产 `JWT_SECRET` 走环境变量注入，密钥长度 ≥ 32 字符（启动即校验，缺失直接启动失败） |

## 七、核心业务流程

### 7.1 下单（`OrderService.create`）

1. 校验：购物车非空 → 归属同一店铺 → 店铺 `business_status=1` 且 `audit_status=1` → 地址归属当前用户。
2. 取菜品：批量 `DishApi.listByIds`，逐个校验 `status=1`、`stock >= quantity`。
3. 算钱（全部后端计算）：`total_amount = Σ(price × quantity)`，`pay_amount = total_amount + delivery_fee`，校验 `total_amount >= min_amount`（起送价），不满足抛 `BELOW_MIN_AMOUNT`。
4. 原子扣库存（逐条 `deductStock`，任一失败抛 `STOCK_NOT_ENOUGH` → 整单回滚）。
5. 落库：`orders`（地址快照）+ `order_item`（菜品快照）+ `payment`（待支付）+ `order_status_log`（→10）。
6. 清空该店铺对应的购物车行。

`@Transactional(rollbackFor = Exception.class)`，库存扣减在事务内，失败全部回滚。

### 7.2 支付（模拟）

`POST /api/customer/payment/{orderNo}/pay` → 校验订单归属与状态为 10 → 支付单置已支付、写 `trade_no`（模拟流水号）→ 订单 10→20、写 `pay_time` → 记状态日志。真实支付接入时，此逻辑原样搬进异步回调接口即可。

### 7.3 超时未支付自动取消

`@Scheduled(fixedDelay = 60s)` 扫描 `status=10 AND create_time < now()-15min` 的订单 → 逐单转 60、归还库存、关闭支付单、记日志。单线程 + 逐单事务，避免长事务锁表。

### 7.4 商家接单/拒单/出餐

接单 20→30；拒单 20→60（归还库存 + 标记待退款）；出餐 30→40；送达 40→50（累加销量）。全部复用 `OrderStatusMachine` 校验合法流转，非法流转抛 `ORDER_STATUS_ERROR`。

## 十二、Vibe Coding 协作流程（怎么用这份方案真正学懂代码）

> 目标：**AI 写代码，理解留给自己**。核心做法是把「读懂」变成每个任务的显式交付物，而不是顺带的产物。
> 反面模式必须避免：一句话让 AI 把整个 P1 写完 → 生成几十个文件 → 你既不敢改也说不清链路。

### 12.1 单个原子任务的五步循环

> 原子任务 = 一个模块（如 `dish`）或一条业务链路（如「下单」）。**不要**一次让 AI 实现整个阶段。

| 步 | 做什么 | 通过标准（不满足就停在这一步） |
| --- | --- | --- |
| ① 先要计划 | 让 AI 只输出「任务拆解 + 文件清单 + 每个文件职责 + 待确认点」，**不写代码** | 你能看懂清单，能说出每个文件为什么必须存在 |
| ② 实现 | 确认计划后让 AI 写代码 | 编译通过 |
| ③ 要导读 | 让 AI 输出「调用链 + 最该看的 3 个文件 + 业务规则表」 | 你能自己复述这条链路 |
| ④ 跑验证 | 启动服务 / 前端，亲手调接口或点页面 | 有可观察结果：Swagger 返回、页面数据、库表变化 |
| ⑤ 追问 + 动手改 | 用 12.3 模板追问，然后**自己改一个小地方**并预测结果 | 改动生效且与你的预期一致 |

**第 ⑤ 步不可省略**：只读不改编不成自己的理解。一次「改动 + 预期验证」，抵十次阅读。
**规模上限**：单个原子任务控制在 5～10 个文件。超了就是拆得不够细，让 AI 重新拆。

### 12.2 各阶段学习锚点

不是所有代码都值得精读。每阶段只需吃透下表内容，其余略读即可（知道它在哪、干什么用）。

| 阶段 | 必须搞懂的锚点 |
| --- | --- |
| P0 | 依赖方向为什么是单向的；`Result` + `GlobalExceptionHandler` 如何把任意异常统一成 JSON；审计字段如何自动填充；`CacheClient` 为什么要做 local/redis 双实现 |
| P1 | `AuthenticationFilter` 六步校验的**顺序**（为什么黑名单要在解析之后）；refresh 旋转为什么能防重放；黑名单 TTL 为什么必须等于令牌剩余有效期；前端并发刷新为什么必须用单例 Promise |
| P2 | api 契约隔离：`dish` 要拿店铺名，为什么必须走 `MerchantApi` 而不是直接查 `merchant` 表 |
| P3 | 订单状态机的合法流转表；事务边界切在哪一层；`UPDATE ... WHERE stock >= ?` 为什么能无锁防超卖；快照字段为什么必须冗余而不能靠 join |
| P4 | 动态路由与菜单如何按 `userType` 注入；数据权限为什么在 Service 层必须再校验一次（路径前缀只能卡到端，卡不到「哪条数据」） |

### 12.3 提问模板（可直接复制使用）

**A. 阶段启动 —— 要计划，不要代码**

```
按方案「P1 认证」实现。先只输出，不要写代码：
1) 任务拆解（做什么、为什么这个顺序）
2) 文件清单（完整路径 + 每个文件一句话职责）
3) 复用了 common 里哪些已有能力
4) 需要我先确认的设计点
等我确认后再动手。
```

**B. 实现后的导读 —— 要地图，不要复述代码**

```
实现完了。用「新人视角」给我导读：
1) 调用链：从 HTTP 入口到落库，逐步列出类 → 方法，标出每一步做了什么校验
2) 我最该优先看懂的 3 个文件，每个说明为什么选它
3) 业务规则清单表：规则 / 代码位置 / 不满足时抛哪个错误码
不要贴代码。
```

把「顾客下单」这条流程从点击到落库完整走一遍：

```

**D. 出题检验 —— 暴露理解偏差**

```
基于 order 模块出 6 道题考我，覆盖状态机、库存扣减、事务边界、权限校验。

```

**E. 改动练习 —— 把理解变成能力**

```
我想把配送费改成按距离阶梯计算。先不要改代码，告诉我：
1) 需要动哪些文件（按模块归类）
2) 会影响哪些已有逻辑
3) 有没有更简单的替代方案
```

**F. 阶段收尾 —— 逼 AI 暴露技术债**

```
本阶段做一次自检：
1) 哪些地方是「先这样、以后再说」的妥协？
2) 哪些设计在二期会遇到瓶颈？
3) 有没有为了通过验证而临时绕过的校验？
只列问题，不要美化。
```
